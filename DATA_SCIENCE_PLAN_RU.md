# Твоя часть: разметка, оценка качества и анализ ошибок

Ты можешь внести содержательный DS-вклад, пока друг делает интерфейс. Начни с человеческой разметки и объяснений ошибок модели. Для чтения диалогов и подготовки эталонов не нужны GPU, новая модель или запуск сайта.

## Что делать по порядку

1. Попросить у команды разрешённый DEV JSON и исходный чек-лист. Держать реальные диалоги локально; не вставлять их в публичные чаты, репозитории и сторонние AI-сервисы.
2. Выбрать небольшую часть текстовых чатов с RU/KZ/EN, разной длиной и разными запросами. Заранее отделить примеры для настройки от отложенных примеров для проверки. Не отбирать проверку по тому, где модель уже ответила хорошо.
3. Сначала оценить диалоги самостоятельно, **не глядя на ответы модели**. Для каждого из восьми критериев записать ответ, номера реплик и краткую причину. Спорные случаи отметить, не выдумывая тарифы и внутренние правила.
4. По возможности дать второму участнику независимо разметить те же диалоги; обсудить расхождения по правилам и сохранить согласованный ответ. Это командная экспертная разметка, а не официальный скрытый Ground Truth.
5. Друг запускает модель и передаёт тебе `runs/dev.json`. Создать `data/dev-labels.json`, затем запустить сравнение командой ниже. Если нет возможности запустить Python, передать JSON с разметкой другу.
6. В отчёте открыть `review_queue`: сначала ошибки грубых нарушений, затем N/A, затем большие расхождения итогового балла. Прочитать сами реплики, а не только объяснение модели.

DEV-звонки организаторы дали преимущественно для UI. Сосредоточить основную проверку точности на чатах; звонки можно разбирать отдельно, не смешивая выводы о качестве с контрольным набором без звонков.

## Формат человеческих ответов

Ниже **пример синтаксиса**, не готовый эталон. Заменить ID и каждый ответ после чтения реального диалога:

```json
{
  "REAL_CONVERSATION_ID": {
    "greeting": "yes",
    "needs": "na",
    "identity": "na",
    "consultation": 15,
    "empathy": "yes",
    "management": 7,
    "closing": "no",
    "critical": "no"
  }
}
```

У каждого включённого ID должны быть **все восемь** ответов. Бинарные ответы: `"yes"`/`"no"`; N/A: строка `"na"` только при разрешённом условии; консультация: 0/5/10/15/20; управление диалогом: 0/4/7/10. В этом внутреннем файле не использовать `true/false/null`: такие типы создаёт отдельный конкурсный экспорт.

Обоснования и ссылки человеческой разметки вести отдельно, например в личной таблице с колонками: ID → критерий → ответ → номера реплик → причина → спорный случай → решение после обсуждения. Пропущенное подтверждение личности не означает N/A. Если исходные сведения не позволяют подтвердить спорный факт, сохранить это ограничение в комментарии.

## Получить отчёт

```powershell
python batch.py compare runs/dev.json data/dev-labels.json --dataset data/dev.json --report runs/dev-analysis.json
```

Команда не вызывает AI. Она сравнивает уже готовые предсказания с твоей разметкой. `--dataset` проверяет соответствие транскриптов и номеров реплик, добавляет разрезы по языкам и каналам.

| Поле отчёта | Как читать |
| --- | --- |
| `labeled`, `matched`, `coverage`, `missing_ids` | Сколько размечено, сколько действительно сравнено, какие оценки отсутствуют |
| `total_mae` | Среднее абсолютное расхождение итогового балла по сопоставимым парам; меньше — лучше |
| `criteria.*.exact_rate` | Доля точных совпадений по конкретному критерию |
| `criteria.*.confusion_matrix` | Строки — человек, столбцы — модель; показывает, какие ответы путаются |
| `criteria.*.na_disagreement` | Сколько раз один поставил N/A, другой — применимую оценку |
| `criteria.*.scale_mae` | Ошибка исходной числовой ступени; пары с N/A исключены |
| `criteria.critical.detection` | TP/FP/FN/TN, precision/recall/F1 для грубых ошибок |
| `review_queue` | Реальные несовпадения с причинами модели, ссылками и аудитом |
| `breakdowns.language` | Раздельная оценка RU/KZ/EN с числом сравнённых диалогов |

`null` в метрике означает, что она не определена на имеющихся парах: например, нет положительных случаев для recall. Это не нулевая точность. Пропавшие оценки не учитываются как идеальные или нулевые: их видно в покрытии. Даже низкий MAE не исключает серьёзных ошибок флага `critical`, поэтому смотреть оба показателя.

На очень маленькой выборке одна ошибка сильно меняет результат. В портфолио указывать число диалогов и ограничения. Общий показатель по всем ответам может скрывать проблемы одного языка или критерия.

## Как улучшать осмысленно

Для каждой ошибки выбрать причину:

- неправильная применимость N/A;
- перепутаны действия клиента, бота и оператора;
- нарушен порядок «идентификация → защищённое действие»;
- перепутаны якоря шкалы полноты ответа;
- грубое нарушение пропущено либо приписано без основания;
- объяснение не поддерживается указанной репликой;
- не хватает данных или есть неоднозначность самого правила/разметки;
- техническая ошибка, обрезанный ответ или неподходящая ссылка.

Менять один фактор за эксперимент: формулировку инструкции, настройки или используемую модель. Для изменённой инструкции обновить `PROMPT_VERSION`, сохранить новый запуск в другой файл, сравнить на той же отложенной выборке. Не подставлять правильные ответы в оценки и не прописывать исключения по ID диалогов. Для разных версий **самого чек-листа** прежние эталоны могут стать неприменимыми: сначала сверить правила и заново разметить затронутые критерии.

Полезный результат для команды: список трёх самых частых типов ошибок, по одному обезличенному примеру каждого, сравнение двух конфигураций с одинаковыми данными и измеренное время обработки на ноутбуке команды. Выбирать изменения по качеству и времени, не по неизвестной формуле отбора.

## Как описать свой вклад в портфолио

После выполнения работы можно написать:

> Подготовила ручную разметку диалогов поддержки по восьми критериям, провела анализ ошибок LLM и оценку качества по MAE, confusion matrices и precision/recall грубых нарушений; исследовала ошибки N/A и различия между RU/KZ/EN.

Добавлять конкретные числа только после реального измерения. Сейчас программные проверки подтверждают работу функций, а точность относительно официальных экспертных оценок не измерена. Для публичного портфолио использовать синтетические/разрешённые обезличенные примеры, без реальных клиентских данных, подписанных ссылок и закрытых материалов организаторов.
