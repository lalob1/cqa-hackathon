# Доработка функций CQA: передать другу

Эта версия объединяет backend-only ZIP с более свежей локальной версией интерфейса. Кнопки фильтров, импорта и апелляций подключены к серверной истории. Новых зависимостей pip нет. Исходный чек-лист `rubric.json` не менялся.

## Как установить

1. Сохранить резервную копию папки проекта или сделать отдельную локальную ветку.
2. Распаковать содержимое этого ZIP **в корень существующего проекта**, туда, где лежит `app.py`. Подтвердить замену `app.py`, `engine.py`, `batch.py`; добавить `results_io.py`, `workflow.py`, новые тесты и инструкции. Все пять Python-файлов нужны вместе.
3. В терминале из этой папки выполнить:

```powershell
python -m unittest discover -s tests -v
python app.py
```

Открыть http://127.0.0.1:8765. Для реальной AI-оценки по-прежнему нужна уже установленная и запущенная локальная модель Ollama/llama.cpp. Тесты работают без модели, скачиваний и обращения к внешнему AI. Python 3.10+ нужен, как и раньше.

## Что работает

| Функция | Где использовать |
| --- | --- |
| Проверка полной структуры ответа, допустимых ступеней, ссылок и обрезанного ответа модели; один повтор с объяснением ошибки | Существующая кнопка оценки, `batch.py score` |
| Уточнённая инструкция о N/A, неполных данных, проверке личности, ботах и спорных фактах | При каждой новой оценке |
| Хеши контекста, чек-листа, запроса и настроек, время, сведения о токенах | Поле `audit` результата |
| Продолжение прерванной оценки, повтор неудачных записей | `batch.py score ... --resume` |
| Confusion matrices, MAE, ошибки N/A, precision/recall грубых ошибок, очередь разбора и разрезы по языкам | `batch.py compare ... --report ...` |
| Импорт пакетных результатов с проверкой исходного транскрипта и пересчётом баллов | `workflow.py import`, `/api/import-results` |
| История запусков, апелляции, решения и фильтры грубых ошибок в SQLite | `workflow.py`, новые API |
| Конкурсный `results.json` с каноническими ID и типами | `results_io.py`, `/api/export-results` |

**Фронтенд подключён:** успешная оценка получает `run_id`, карточка использует полный серверный запуск, апелляции и решения сохраняются в SQLite. Контракты описаны в [API_FOR_FRONTEND.md](API_FOR_FRONTEND.md).

Старые апелляции интерфейса остаются в localStorage браузера. Они автоматически не переносятся в SQLite. Кнопка «Сохранить запуск на сервере» переносит старую историю с резервной копией; новые формы используют `/api/appeals` и `/api/reviews`, а ответы сервера считают актуальным состоянием; старый `/api/recalculate` просто считает балл и не сохраняет решение.

## Оценить набор и восстановить запуск

Использовать исходный JSON, полученный от организаторов. Поддерживаются их API-обёртка, массив диалогов и один объект диалога.

```powershell
python batch.py score data/dev.json --output runs/dev.json
```

Если выполнение прервалось или были ошибки:

```powershell
python batch.py score data/dev.json --output runs/dev.json --resume
```

Повторно используются только проверенные успешные записи. Ошибки и ещё не обработанные диалоги оцениваются снова. Если изменились данные, чек-лист, модель, адрес локального сервера или настройки, продолжение блокируется: выбрать **новый выходной файл** и оценить заново. Старые результаты без нового manifest также требуют нового запуска. Один и тот же псевдоним модели не гарантирует неизменность её весов: перед контрольным запуском зафиксировать установленную версию модели.

Чтобы использовать изменённый чек-лист, добавить `--rubric rubric-custom.json`. Он действительно попадает в запрос модели. Старые оценки не пересчитывают смысл нового критерия: для этого нужен новый AI-запуск.

## Разбор ошибок — часть Токи

```powershell
python batch.py compare runs/dev.json data/dev-labels.json --dataset data/dev.json --report runs/dev-analysis.json
```

Файл `dev-labels.json` нужно заполнить вручную по исходному чек-листу: полная карта ответов на каждый размеченный диалог. Пример формата есть в [DATA_SCIENCE_PLAN_RU.md](DATA_SCIENCE_PLAN_RU.md). Без человеческих эталонов нет измеренной точности. Ошибка обработки не превращается в нулевой балл, а неразмеченные предсказания не входят в метрики.

## Импортировать пакет в локальную историю

```powershell
python workflow.py import --input runs/dev.json --dataset data/dev.json
python workflow.py list --filter critical
python workflow.py list --filter appeal
python workflow.py show RUN_ID
```

`RUN_ID` заменить идентификатором из ответа `import` или `/api/score`. Вывод `list` содержит причины грубых ошибок и ссылки на реплики. По умолчанию показывается последний сохранённый запуск каждого диалога; `--all-runs` показывает историю, `--offset` и `--limit` — страницы.

`critical` фильтрует исходные флаги модели. `final-critical` учитывает решения проверяющего. Снятый после апелляции флаг сохраняется в исходной истории.

Апелляции можно проверить без нового фронтенда:

```powershell
python workflow.py appeal RUN_ID consultation --message "Прошу пересмотреть полноту ответа" --revision 0
python workflow.py show RUN_ID
python workflow.py decide RUN_ID APPEAL_ID --answer 20 --reason "Все вопросы закрыты; см. указанные реплики" --revision 1
```

Это пример для числовой шкалы `consultation`: реальное решение выбрать по диалогу и якорям шкалы. `APPEAL_ID` взять из массива `appeals`. Для бинарных ответов CLI ожидает JSON-строку `"yes"`, `"no"` или разрешённое `"na"`. В Windows удобнее использовать API-пример с `ConvertTo-Json` из инструкции другу: он избегает неоднозначного экранирования кавычек в разных версиях PowerShell.

`revision` брать из актуального ответа сервера. Устаревшее или повторное решение отклоняется; исходные оценки не перезаписываются.

## Подготовить конкурсную выгрузку

```powershell
python batch.py score data/prod.json --output runs/prod.json
python results_io.py --input runs/prod.json --dataset data/prod.json --group prod --team "TEAM_NAME" --output results/prod/results.json
```

Для DEV: заменить пути и `--group dev`; выход `results/dev/results.json`. DEV проверяется как 65 записей (60 чатов, 5 звонков), PROD как 10 чатов. `group_id` в ссылке скачивания может называться иначе: здесь `dev/prod` обозначает тип конкурсной выгрузки.

Экспорт требует исходный конкурсный чек-лист: восемь критериев, исходные правила, веса и шкалы. После экспериментов вернуть его и запустить оценку отдельно. Изменённый рабочий чек-лист остаётся доступен для демонстрации редактора.

Выгружаются **исходные ответы модели**, без ручных решений апелляций. `yes/no/na` преобразуются в `true/false/null`, шкалы сохраняют исходные ступени. Номера реплик считаются во всём транскрипте, включая клиента, бота и систему. Пропущенные или неудачные оценки остаются строками `status: "error"`, `score: null`; файл с такими строками неполон и требует исправления. Код выхода CLI: 0 — успешно, 1 — есть ошибки/неполное покрытие, 2 — некорректные данные или команда.

Не публиковать `data/`, `runs/`, локальную базу, реальные транскрипты и подписанный URL. Конкурсный файл передавать только способом, который указали организаторы. Никакой автоматической публикации или push в этих командах нет.

## Проверено и что ещё остаётся

Проверены расчёты, продолжение после прерывания, HTTP API, сохранение истории, конкурентные решения, экспорт и валидация. Модель в тестах подменена управляемыми ответами. Это проверка работы программы, а не доказательство близости к Ground Truth.

Дальше: измерить метрики на размеченной части DEV, разобрать спорные решения, проверить время оценки на ноутбуке команды и подключить новые API к фронтенду. Новое распознавание звонков сейчас имеет меньший приоритет: в контрольном наборе звонков не будет.

Хранилище по умолчанию: `data/cqa.sqlite3`; переменная `CQA_DB` меняет путь. База хранит тексты и историю на компьютере, не является шифрованным хранилищем. Это локальный прототип без регистрации: имя проверяющего — подпись, а не подтверждённая учётная запись. Не открывать этот сервер в интернет. Хеши связывают файлы и настройки, но не являются криптографическим доказательством авторства модели или гарантией одинакового вывода на разном железе.
