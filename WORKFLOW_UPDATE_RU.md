# Проверка DEV и серверный процесс пересмотра

Обновление от 8 ноября 2026 года. Основа — актуальная ветка `model/compact-transcripts` и переданный backend-only ZIP. Существующий интерфейс, локальные адаптеры модели и расчёт баллов сохранены. Полный разбор выбранных переписок хранится локально; сводка эксперимента — в `DEV_REVIEW_SUMMARY.md`.

## Что изменилось

- `app.py`, `workflow.py`: исходные оценки, снимок диалога и чек-листа, апелляции и неизменяемая история решений сохраняются в SQLite. Каждое изменение проверяет `expected_revision`.
- `web/app.js`, `web/index.html`, `web/style.css`: импорт CLI-оценок, восстановление истории с сервера, фильтры исходных и финальных грубых ошибок, открытых апелляций и неоценённых загрузок. Последний запуск выбирается до фильтрации; текст переписки не используется для фильтра грубых ошибок.
- Карточка сохраняет исходное объяснение ИИ и его доказательства отдельно от решения проверяющего. Из фильтра проблемный критерий открывается сразу. Повторная апелляция добавляет запись в историю.
- При HTTP 409 приложение загружает актуальный запуск и показывает неотправленный черновик. Автоматического повторного сохранения с новой ревизией нет. После сверки пользователь отправляет его явно.
- Ошибки пакетного импорта показываются отдельным списком и сохраняются в браузере. Повторный импорт того же запуска сохраняет его серверный ID и решения.
- Если новый пакет содержит ошибку по уже оценённому ID, новая оценка не создаётся. Карточка и фильтры продолжают использовать последний успешный сохранённый запуск; его версию видно в «О запуске», а новая ошибка остаётся отдельным сообщением. Старый балл нельзя считать результатом неудавшегося прогона.
- Другой транскрипт или метаданные под уже сохранённым ID отклоняются: весь пакет откатывается, существующие оценки и апелляции сохраняются.
- Старые браузерные запуски доступны для чтения. Кнопка переноса на сервер сохраняет резервную копию их исходной истории и проверяет конфликты.
- `engine.py`: сохраняет компактный полный транскрипт, проверяет доказательства и делает повторный запрос только по невалидным критериям. Уже принятые ответы при повторе не изменяются. Модель получает полный текущий чек-лист и переписку и при повторе.
- При исправлении модель получает список допустимых номеров реплик оператора и сообщение о конкретном противоречии. Внутреннее рассуждение в этот контекст и сохранённые данные не попадает.
- Проверки доказательств относятся к неизменённым стандартным правилам. Они отклоняют приписывание действий клиента/бота оператору и несколько обнаруженных в разборе противоречий: отсутствие уточняющего запроса в доказательстве, одни формулы прощания вместо двух действий завершения и распознанное раскрытие статуса счёта без предшествующей проверки. Это ограниченные проверки, а не полная семантическая экспертиза. Они запрашивают исправление у модели, а не вставляют заранее размеченные ответы.
- Итоговая V11 дополнительно проверяет явное закрытие чата оператором при ответе N/A, наличие прощания в положительной ссылке завершения, несколько прямых формулировок предложения платного частного совета и точное совпадение объяснения с якорем другой числовой ступени. Проверки узкие: они не подтверждают корректность остальных объяснений. Исторические результаты разрешено импортировать для пересмотра; эти live-проверки их не переписывают.
- `results_io.py`: проверяет ID, исходный транскрипт, снимок чек-листа, типы ответов, номера реплик и версию промпта; баллы пересчитываются. Конкурсный экспорт отделён от внутренних результатов и ручных решений.
- `batch.py`: сохранены атомарные контрольные файлы, блокировка второго писателя, `--resume`, `--expect-count`, `--model-revision` и `export`. Сравнение дополнено матрицами ошибок, N/A, грубыми нарушениями, языками и очередью проверки.

## Запуск

Нужен Python 3.10+. Новых зависимостей pip нет.

```powershell
python app.py
```

Откройте http://127.0.0.1:8765. Просмотр импортированных оценок и пересмотр работают без модели. Для нового анализа настройте один из локальных адаптеров из README.

Для уже запущенного llama.cpp:

```powershell
$env:CQA_PROVIDER = "llamacpp"
$env:CQA_LLAMA_URL = "http://127.0.0.1:18880"
$env:CQA_TIMEOUT_SECONDS = "420"
python app.py
```

Имя настроенной модели и `/api/health` не подтверждают доступность inference. Успех или ошибка реального запроса показываются в интерфейсе.

Для Qwen выбран включённый режим рассуждения. `CQA_THINKING=0` отключает его для сравнительного прогона или модели, которая его не поддерживает. В llama.cpp `CQA_REASONING_BUDGET` ограничивает внутреннее рассуждение (по умолчанию 1536 токенов); окончательный JSON имеет отдельный запас в общем лимите ответа. Для медленной машины таймаут можно увеличить до 600 секунд. Параметры записываются в каждом запуске. В результатах сохраняются итоговые объяснения и факт наличия рассуждения, а не его внутренний текст.

Адаптер llama.cpp использует поддержанный установленной сборкой b11719 параметр `thinking_budget_tokens`; проверена [реализация разбора запроса](https://github.com/ggml-org/llama.cpp/blob/b11719/tools/server/server-common.cpp). У Ollama используется [поле `think`](https://docs.ollama.com/capabilities/thinking); отдельного проверенного бюджета рассуждения для этого адаптера нет. Live-проверки этой задачи выполнялись через llama.cpp.

SQLite по умолчанию: `data/cqa.sqlite3`; другой путь задаётся через `CQA_DB`. Оценённые диалоги восстанавливаются с сервера. Настройки редактора, ещё не оценённые загрузки и черновики хранятся в браузере. Это локальный прототип без авторизации; имя проверяющего не является подтверждённой учётной записью.

## Проверка основного сценария

1. Загрузить новый JSON диалога и нажать «Оценить диалог». Для повторения демонстрации есть синтетический [examples/review-flow.json](examples/review-flow.json); это не DEV или PROD.
2. Открыть критерий, сравнить объяснение с исходными репликами и перейти по ссылке доказательства.
3. Нажать «Оспорить оценку», добавить комментарий и сохранить.
4. Выбрать решение проверяющего, указать причину и сохранить. Сверить новый итог с исходной оценкой.
5. Перезагрузить страницу. История и оба результата должны восстановиться.
6. Изменить формулировку, вес или добавить критерий в редакторе, сохранить и сделать новый запуск. Старый запуск должен сохранить собственный чек-лист.
7. Загрузить исходные диалоги, затем через «Другие действия → Импорт оценок» импортировать внутренний JSON от CLI. Проверить фильтры и апелляцию на импортированном запуске.

При проверке двух вкладок сначала открыть форму в первой, затем изменить тот же запуск во второй. Сохранение устаревшей формы должно вернуть 409, сохранить черновик и потребовать сверки актуального состояния.

```powershell
python -m unittest discover -s tests -v
node --check web/app.js
python batch.py compare runs/dev.json data/dev-labels.json --dataset data/dev.json --report runs/dev-analysis.json
```

Команда `compare` не вызывает модель. Разметка, выполненная ассистентом, не является официальным Ground Truth или независимой разметкой команды; спорные ответы нужно согласовать с человеком.

## Экспорт

```powershell
python batch.py export data/dev.json runs/dev.json --group dev --team-name Democrats
python batch.py export data/prod.json runs/prod.json --group prod --team-name Democrats
```

Для DEV проверяются 60 чатов и пять звонков, для PROD — 10 чатов. Ошибка обработки сохраняется как `status="error"`, пустые критерии и `score=null`, с исходным ID и причиной. Экспорт не подмешивает решения проверяющего в исходные AI-ответы. Неполнота не означает нулевой балл и не должна скрываться.

Восемь стандартных критериев и исходный `rubric.json` сохранены. Рабочий изменённый чек-лист можно импортировать и пересматривать, но произвольный девятый критерий не помещается в конкурсную схему.

Существующий DEV-экспорт предыдущего полного прогона не следует считать переоценкой всех 65 диалогов новой версией. Текущая задача проверяет небольшую выбранную часть. Реальный контрольный набор и отправка организаторам в эту проверку не входят.
